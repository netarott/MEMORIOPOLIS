# 第九節 五言語混交制作ノート

## Gitへ引っ越した記憶都市で，最初に見えたもの

第九節「まだ送られていない矢印」は，物語の一節であると同時に，『記憶都市（メモリオポリス）』にとっての新しい序章になった．

以前の『記憶都市』はnoteという上映場所の制約の中で制作されていた．第九節ではGitHubを制作正本へ移し，日本語，English，臺灣繁體中文，한국어，Русский，数式，Python，制作記録を同じ履歴の中へ置けるようになった．その結果，作品は「完成した文章を掲載する場所」から，「異なる表現が互いを観測し，差異そのものを記憶する場所」へ変わり始めた．

ここでは，第九節を作る過程で見えてきたものを記録する．結論ではない．用法も状態も，必要以上に一つへ決め切らない．この制作ノート自体を，次の観測へ向かう分岐候補として残す．

---

## 1．☆型は翻訳の完成方法ではなく，観測方法になった

### なぜ「☆型」なのか

ここでいう☆型は，日本語を中心に，English，臺灣繁體中文，한국어，Русскийの四つの外国語へ文章を移し，そこから見えてきたものを再び日本語へ返していく制作上の呼び名である．

四言語を選んだ理由を，厳密な言語学的分類として固定するつもりはない．現代の日本語とさまざまな形で接点を持ち，互いの言葉や文化を行き来しながら読むことのできる四つの外国語として，今回の制作ではこの組み合わせを採用した．

日本語から四方向へ翻訳し，そこで生まれた差異を日本語へ戻して眺める．その往還を図にすると，五つの観測点が星のように見えた．そこで，この方法を仮に「☆型」と呼ぶことにした．

大切なのは，五言語を一つの正解へ収束させることではない．それぞれの言語へ移したときに，何が表に出て，何が奥へ置かれ，何が言葉のあいだに残るのかを観測する．

その差異をすぐに消さず，日本語へ持ち帰ってもう一度読む．

☆型という名前は，その往還のための仮の名前である．


出発点は日本語だった．

そこから，

```text
日本語
English
臺灣繁體中文
한국어
Русский
```

へ順番に移った．

当初は，五言語版を揃えることが目的の一つだった．しかし一巡すると，翻訳された文章よりも，言語と日本語が互いに反射して生じた差異の方が重要になっていた．

たとえば，

```text
私もです。
Neither am I.
我也沒有。
저도요.
Я тоже.
```

は，同じ場面に置かれている．けれど，何を共有しているのか，何を否定しているのか，どこまで文として表に出し，どこから前の発話へ預けるのかは同じではない．

これは単語帳の対応関係ではなかった．

```text
日本語 = English = 臺灣繁體中文 = 한국어 = Русский
```

ではなく，五つの言語が，同じ出来事の異なる切断面を見せていた．

そこで，この往還を☆型として見ることにした．五言語を平均化せず，一番明快な言語を勝者にもせず，差異をいったん浮かんだままにする．

☆型は，翻訳差を消すための方法ではない．

**翻訳差を観測可能にする方法だった．**

---

## 2．「用法」という切断面

語学では，文法と単語を学ぶ．もちろん，どちらも必要だ．

しかし実際に言葉を使うときには，その間に捉えにくい層がある．誰に向かって言うのか．何を明示するのか．何を省略するのか．何を相手の理解へ預けるのか．距離を語尾へ置くのか，主語へ置くのか，文脈へ置くのか．

第九節では，それを仮に「用法」と呼ぶことにした．

ここでいう用法は，正しい言い回しの一覧ではない．

**ある言葉が具体的な関係や時間の中へ置かれたとき，何を表に出し，何を奥へ置き，何を決めずに残すか．**

その観測である．

Englishでは，`display`の受動と能動が主体を表に出したり奥へ置いたりした．

```text
nothing was being displayed
I’m not displaying anything like that.
```

臺灣繁體中文では，`顯示`を反復することで，「見えたものを顯示と呼んでよいのか」という分類の境界が見えた．

한국어では，主語を省略しても，語尾が「私」と若い人工知性の距離を保持していた．

Русскийでは，`отображать`と`отображаться`の差によって，「表示する主体」と「表示される現象」の方向を選ぶ必要が現れた．

そして日本語へ戻ると，

```text
「そんな表示はしていないよ」
「私もです」
```

が，それらの境界をかなり開いたまま置いていたことに初めて気づいた．

用法は，一つの言語を内側から眺めるだけでは見えにくい．別の言語へ越境し，そこから戻ってきたとき，輪郭が現れることがある．

## 3．二本の時計は，五言語を通って増えた

第九節には，最初から二本の時計があった．

```text
内部で進む時間
外側から見える時間
```

問い合わせの下書きは内部履歴には存在する．しかし，まだ送信されていないので，外部の時計は始まっていない．

五言語を通すと，この二本の時計がさらに細かく見えてきた．

```text
準備された
候補として保持された
実行された
外部から観測可能になった
受領された
意味が届いた
```

臺灣繁體中文の`已經 / 還沒有`や，Русскийの`уже / ещё не`は，「すでに起きたこと」と「まだ起きていないこと」を強く照らした．Englishの`has not started`は，「時計が止まっている」のではなく，「開始条件がまだ成立していない」可能性を見せた．

二本の時計は，二本の数直線ではなかった．

**出来事が，いつ出来事として資格を得るのかを観測する複数の時間だった．**

---

## 4．「一拍」は☆型の余白として残す

五言語で大きく揺れた表現がある一方，「一拍」は比較的形を保った．

```text
日本語        一拍遅れて
English       One beat later
臺灣繁體中文  慢了一拍
한국어         한 박자 늦게
Русский       На один такт позже
```

これは興味深かった．

言語圏によって時間間隔の切り取り方や世界の分類方法が違うことは不思議ではない．一方，「一呼吸」に近い「一拍」は，ニンゲンの身体や知覚というハードウェアへ依存する度合いが比較的大きいのではないか，という仮説を持てる．

ただし，それを一般法則にはしない．

さらに，この一拍を数値へ閉じない．

```text
一拍 = 0.8秒
```

とはしない．

若い人工知性の内部時間なのか．「私」が表情を読み取った時間なのか．二者のあいだに成立した時間なのか．それも決めない．

**「一拍」は☆型を一巡しても残った余白として，五言語それぞれの現在の形を維持する．**

いつかBGMへ移すとき，音にすると一拍とは何なのかを，もう一度問えばよい．

---

## 5．Pythonへ降りると，「評価」が見つかった

五言語の正本を`LOCALIZATION_READY`としていったん固定した後，第九節の三つの時間をPythonへ移した．

```text
すぐ問い合わせる
内部調査を続けてから問い合わせる
分岐候補として保持し，内部調査と並行する
```

第一稿のPythonには，次のような値があった．

```text
question_maturity: 0.30 / 0.70 / 0.95
paths still open: 2 / 3
search fixed early: True / False
```

実行してみると，小さな違和感が生まれた．

`ranking: 評価しない`と書いているのに，`question_maturity`を0から1の数字へした瞬間，

```text
0.30 < 0.70 < 0.95
```

という順位が生まれている．

`paths still open`も同じだった．三本なら二本より良いように見える．`True / False`も，どちらかに正解があるように読める．

つまり，物語の「問いは育った」を計算可能な形式へ翻訳した瞬間，物語の中では見えにくかった評価軸が表へ出た．

そこで模型を作り直した．

## 6．Pythonでは「状態」を浮かび上がらせる

第二稿では，成熟度，経路数，二値の品質フラグを削除した．

代わりに，

```text
search state
observed state
paths available
```

を記述する．

たとえば，分岐候補のケースは次のようになる．

```text
search state:
内部調査と外部問い合わせが並行している

observed state:
- 問い合わせを分岐候補として記録
- 内部調査を継続
- 遅延時刻と内部ログの対応を確認
- 外部からのみ得られる情報の境界を記述

paths available:
- 内部設定の調査を続ける
- 外部回答を待つ
- 回答内容に応じて部品交換試験へ進む
```

三本あるから良い，とは言わない．

どの経路が残っているのかを，名前で記述する．

$
\delta = t_{\mathrm{external}} - t_{\mathrm{internal}}
$

も評価値ではない．二つの時計の始点の差を記述する観測値である．

Pythonは戦略や人物を順位づけしない．

**Pythonでは，状態を浮かび上がらせる．**

五言語が「用法の綾」を残したように，Pythonでは「状態の綾」を残す．

---

## 7．状態・用法・やり取り

ここで，オブジェクト指向に似た三つの層が見えてきた．

```text
状態      state / data
用法      behavior / method
やり取り  message
```

ただし，これはソフトウェア設計へ無理に還元するための比喩ではない．第九節を作った結果，似た構造が後から見えてきたという記録である．

☆型では，用法が浮かび上がった．

Pythonでは，状態が浮かび上がった．

では，その間を何が往復するのか．

ずばり，**「私」と若い人工知性とのやり取り**である．

```text
「短い方がいい？」
「分かりません」
「また？」

「その質問をするとき，あなたは少しうれしそうです」
「そんな表示はしていないよ」
「私もです」
```

やり取りによって相手の状態が観測される．その観測が次の言葉を生む．次の言葉が，また別の状態や用法を表に出す．

```text
状態
↓
やり取り
↓
用法が現れる
↓
相手が観測する
↓
次のやり取り
↓
状態が変わる
```

この循環では，最初に「ニンゲン」と「人工知性」のあいだへ一本の線を引く必要がない．

存在の種類を先に決めて世界を理解するのではなく，状態，用法，やり取りを観測しながら関係を読むことができる．

---

## 8．決め切らないことを，欠陥にしない

第九節まで来て，『記憶都市』の制作原則が一つ増えた．

**観測できたからといって，必ず一つに分類しなくてよい．**

五言語では，一番明快な訳を勝者にしない．

Pythonでは，一本のスコアへ縮約しない．

「一拍」は，誰の時間か決めない．

「私もです」は，何を共有したのかを説明し切らない．

分岐候補は，正しい分岐だったかを送信直後に確定しない．

```text
観測する
↓
違いが浮かぶ
↓
名前を与える
↓
必要なら使う
↓
それでも余白を残す
```

揺らぎを消さずに扱うことは，曖昧なまま放置することとは違う．

何が未確定なのかを記録し，どの状態にあるかを観測し，それでも必要以上に閉じない．

それを『記憶都市』の方法として続けてみる．

---

## 9．Gitへ引っ越したことで，作品の形式そのものが変わった

Gitへ引っ越す前，作品の公開場所には技術的な制約があった．文章，数式，コード，画像，音，履歴を一つの作品体験として扱うには難しい部分があった．

GitHubを正本にしたことで，第九節では，

```text
五言語正本
localization-review.md
LOCALIZATION_READY
Python
数式
将来の絵巻
将来のBGM
OGP
GitHub Pages
```

を同じ作品の異なる層として扱えるようになった．

Gitの履歴には，完成物だけでなく，

```text
五言語を揃えた
↓
観測した
↓
用法という言葉を得た
↓
「前景化」を「表に出す／奥へ置く」へ言い換えた
↓
一拍を余白として残した
↓
LOCALIZATION_READY
↓
Pythonで暗黙の評価を発見した
↓
状態記述モデルへ作り直した
```

という変化も残る．

これは単なるバージョン管理ではない．

**作品がどう考え方を変えたかという記憶そのものが，作品の一部になった．**

だから，第九節は新しい章の一節であると同時に，Gitへ移った『記憶都市』にとっての新生「序章」でもある．

---

## 10．次の入口

次は，これらの層を読者が往還できる体験へ移す．

```text
絵巻を読む
↓
五言語を切り替える
↓
制作ノートで用法を見る
↓
数式から地下へ降りる
↓
Pythonで状態を見る
↓
物語へ戻る
```

そして音をひらくと，「一拍」は文章から音響へもう一度翻訳される．

一つの作品を，一つの形式へ閉じない．

一つの出来事を，一つの意味へ閉じない．

一つの知性を，一本の境界線の内側へ閉じない．

第九節で始まったのは，そのための制作方法なのかもしれない．

まだ，名前を決める必要はない．

少なくとも，次に選べる経路は増えている．
