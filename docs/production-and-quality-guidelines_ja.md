## 1．この文書の目的

この文書は，『記憶都市（メモリオポリス）』の制作方針，表記規則，リポジトリ構成，自動チェック候補，公開条件を引き継ぐための記録である．

会話や作者個人の記憶だけに規則を置かず，GitHub上の可視履歴として保存する．新しい規則を決めた場合，まずこの文書へ追記し，必要に応じて自動チェックへ翻訳する．

この文書自体も完成品ではなく，制作工程とともに更新する．

## 2．編集方針

### 2.1 制作正本

GitHubを『記憶都市』の制作正本とする．

まず，次の要素をGitHub上で推敲・検証する．

1. 日本語小説本文
2. 数式
3. 必要に応じたPython模型
4. 実行結果と合成データ

日本語正本の確定後，五言語版，五言語混交制作ノート，コミック版を制作する．

### 2.2 公開順序

```text
日本語本文
＋
数式
＋
必要に応じたPython
↓
日本語正本の確定
↓
五言語への文学的ローカライズ
↓
五言語混交制作ノート
↓
コミック版
↓
note公開
↓
各SNSへ共有
```

毎日のnote更新を制作目標にしない．日付ではなく，作品の完成条件に基づいて公開する．

### 2.3 GitHub，note，SNSの役割

#### GitHub

- 制作正本
- 推敲履歴
- 数式
- Python模型
- 五言語版
- 五言語混交制作ノート
- コミック原版
- 品質チェック

#### note

- 完成した作品への入口
- サムネイル
- 短い導入または冒頭
- GitHub正本へのリンク
- マガジンによる連載順の提示

#### SNS

- 新しい作品が公開されたことを知らせる灯り
- 過剰な媒体別最適化は行わない
- 反応は順位づけではなく観測として扱う

## 3．三層の制作原理

『記憶都市』の制作と公開は，次の三層で捉える．

### 記憶

出来事，本文，数式，コード，画像，判断理由，変更履歴を保存する．

### 翻訳

日本語から各言語へ，自然言語から数式へ，数式からPythonへ，小説からコミックへ翻訳する．

### 越境

GitHubからnoteへ，noteからSNSへ，作品から読者へ，正本から派生版へ橋を架ける．

## 5．句読点

### 5.1 小説本文

日本語小説本文では「、。」を使う．

```text
三時間は、三時間だった。
それでも、同じ時間ではなかった。
```

### 5.2 五言語混交制作ノート

日本語構文を骨格とする五言語混交制作ノートでは「，．」を基本とする．

```text
この節では，clock time の equality を出発点にして，同じ三時間の内側へ降りた．
```

### 5.3 例外

- 小説本文からの引用は原文の句読点を保持する．
- 独立した外国語文は原言語の句読点を保持する．
- 数式とコードは各記法を保持する．

## 6．GitHub正本の数式規則

### 6.1 インライン数式

インライン数式は単一のドル記号で囲む．

数式の外側，前後には半角スペースを入れる．

```markdown
「この $\delta$ は？」
```

開き括弧の直後に数式が来る場合も，開き括弧と数式の間へ半角スペースを入れる．

```markdown
「 $t_{\mathrm{internal}}$ は？」
```

```markdown
どれも、短い $\delta$、長い $\delta$ だけでは説明できなかった。
```

ドル記号の内側には余分な空白を入れない．

### 6.2 ブロック数式

短いブロック数式は，一行の `$$...$$` 形式で記述する．

```markdown
$$\delta = t_{\mathrm{external}} - t_{\mathrm{internal}}$$
```

当面，短い式を複数行へ分割しない．Markdownの区切り線や見出しとして誤解釈される可能性を避けるためである．

### 6.3 LaTeXコマンド

バックスラッシュは一つだけ記述する．

正：

```markdown
$\delta$
```

誤：

```markdown
$\\delta$
```

説明語として用いる添字には `\mathrm{...}` を使う．

```markdown
$t_{\mathrm{internal}}$
$t_{\mathrm{external}}$
```

### 6.4 禁止する記法

GitHub正本には，note専用のインライン数式を入れない．

```markdown
$${\delta}$$
```

noteには正本本文を複製せず，GitHub正本への案内を置くため，note記法への機械変換は原則として行わない．

### インライン数式と各言語の正書法

インライン数式は，単一のドル記号で囲む．

通常の単語とインライン数式の境界には，半角スペースを入れる．

```markdown
“What does $\delta$ mean?”
```

ただし，句読点の前後は，各言語の正書法に従う．

英語では，疑問符や感嘆符の直前に半角スペースを置かない．
```markdown
Is the value $\delta$?
The value is $\delta$.
```

次の表記は，英語として不自然になるため避ける．
```markdown
Is the value $\delta$ ?
```

共通規則を機械的に適用して各言語の自然さを損なう場合は，単に空白を追加するのではなく，その言語で自然な文へローカライズする．
例：
```markdown
“What is this $\delta$?”
```
を，次のように再構成する．
```markdown
“What does $\delta$ mean?”
```

自動チェックは，表記上の問題が起き得る箇所を検出する監査役である．最終的な修正方法は，各言語の正書法と文学的な自然さに基づいて判断する．

## 9．自動チェックの現在地

Markdown数式表記を検査する仕組みを，次の構成で導入する．

```text
scripts/check_markdown_math.py
.github/workflows/check-markdown-math.yml
```

GitHub ActionsはPushまたはPull Requestを契機に実行する．

### 現在の検査候補

- [ ] note専用の `$${...}$$` がGitHub正本へ混入していないか
- [ ] インライン数式が `$...$` になっているか
- [ ] インライン数式の前後に半角スペースがあるか
- [ ] ドル記号の内側に不要な空白がないか
- [ ] LaTeXコマンドのバックスラッシュが二重になっていないか
- [ ] 短いブロック数式が一行の `$$...$$` になっているか
- [ ] コードブロック内を誤検出していないか

### 動作確認方針

第九節以降の執筆・Pushで，実際の検査結果を確認する．誤検出や検出漏れがあれば，チェック用Pythonを修正する．

自動チェックは本文を勝手に修正せず，違反箇所と行番号を報告する監査役とする．

## 11．品質チェックを追加するときの原則

1. 人間が繰り返し間違える規則を優先して自動化する．
2. 文学的判断を単純な合否へ落とし込まない．
3. 自動修正より，行番号付きの報告を優先する．
4. 誤検出が多い規則は強制しない．
5. 実際の制作で必要になった規則から追加する．
6. チェック機能自体もGitの履歴へ残す．
7. 正本を守るための仕組みが，創作を妨げる新しい完璧主義にならないよう注意する．
